**1. 项目名**
- 项目名称：美年大健康
- 项目代号：`mnd-health-hub`

**2. 项目使用方与系统架构**
本项目为体检机构使用的综合业务管理系统，采用 Spring Boot + Vue3 技术栈，前后端分离架构。系统划分为两个终端：
- **业务端（front）**：面向普通用户，供购买或参与体检的个人使用；
- **MIS端（mis）**：面向机构内部人员，包括客服与医生，用于后台管理与业务处理。

**3. 核心业务流程**
有体检需求的用户可通过 PC 浏览器或移动端小程序访问业务端（类似电商平台），浏览并选择适宜的体检套餐，完成下单与支付操作。支付成功后，用户可在线预约体检时间。预约生效后，用户于约定时间携带本人身份证前往体检机构，通过人脸识别签到核验身份，随后进行体检。体检过程中由医生录入检查结果，系统最终生成并出具体检报告。

**4. MySQL三高集群搭建方案**
该项目在技术架构上的一大亮点是自主研发并部署了一套生产级高可用 MySQL 集群。集群采用“双主四从”架构：两个主节点通过双向同步保障高可用，每个主节点下挂载两个从节点以实现读写分离。同时，集群集成了 MySQL 官方提供的 MGR（组复制）能力，支持主节点故障时的自动切换，无需人工介入。前端通过 ShardingSphere-Proxy 作为统一数据库入口，自动将写请求路由至主库、读请求分发至从库。此外，我搭建了 ZooKeeper 作为配置中心，并编写 Python 脚本实时监控 MGR 状态。一旦主节点发生切换，脚本自动更新 ZooKeeper 中的配置，ShardingSphere-Proxy 无需重启即可感知变更，确保故障转移对业务层完全透明。整套集群已在 Docker 环境下完成全流程测试，主从同步延迟控制在毫秒级，故障切换时间稳定在数秒以内，满足生产环境标准。

**5. 商品快照存储选型：MongoDB vs MySQL**
商品快照数据采用 MongoDB 存储，主要基于其灵活的 JSON 文档模型，能够天然适配快照的结构化特征，提升开发效率与查询性能。而 MySQL 的优势在于事务一致性，但在快照场景下该优势并不突出，因此未作为首选。

**6. MongoDB vs HBase 选型理由**
在技术选型过程中，我们评估了 MongoDB（适用于 TB 级数据）与 HBase（适用于 PB 级数据）。考虑到体检系统的数据规模与业务复杂度，MongoDB 更加契合实际需求，配合对象存储管理大文件即可满足业务发展。HBase 更适用于超大规模数据场景，在当前业务阶段属于过度设计，因此未予采用。

**7. Sa-Token 令牌颁发流程**
1. 系统首先校验用户提交的用户名与密码；
2. 验证通过后，手动调用 `StpUtil.login(userId)`，由 Sa-Token 框架自动生成令牌，并将令牌及用户信息存入 Redis；
3. 通过 `StpUtil.getTokenValue()` 获取生成的令牌；
4. 将令牌以 JSON 格式返回前端，前端接收后存储于 `localStorage` 中。

**8. Sa-Token 令牌验证机制**
示例代码：
```java
@RestController
@RequestMapping("/mis/user")
public class UserController {
    @GetMapping("/findUser")
    @SaCheckLogin
    public R findUser() { ... }
}
```
验证原理：
- `@SaCheckLogin` 注解拦截请求，提取前端提交的 token；
- Sa-Token 框架在 Redis 中校验 token 有效性；
- 若有效，放行并允许调用接口方法；
- 若无效，抛出 `NotLoginException`，返回 401 未登录状态。

**9. Sa-Token 权限校验（鉴权）**
示例代码：
```java
@PostMapping("/searchByPage")
@SaCheckPermission(value = {"ROOT", "APPOINTMENT:SELECT"}, mode = SaMode.OR)
public R searchByPage(@RequestBody @Valid SearchAppointmentByPageForm form) { ... }
```
原理说明：
- `@SaCheckPermission` 注解同时完成令牌验证与权限校验，无需再使用 `@SaCheckLogin`；
- 令牌有效后，Sa-Token 自动调用 `StpInterface` 的 `getPermissionList` 方法，获取当前用户的所有权限集合；
- 框架校验该集合是否包含 `ROOT` 或 `APPOINTMENT:SELECT`，任一匹配则放行；
- 注解中的权限值必须来源于数据库 `sys_permission` 表的 `permission_code` 字段，不可随意定义。

若需基于角色鉴权，可使用 `@SaCheckRole`，例如：
```java
@SaCheckRole(value = {"CEO", "PO"}, mode = SaMode.OR)
```
此时 Sa-Token 会调用 `StpInterface` 的 `getRoleList` 方法进行角色校验。

**10. 用户权限是否返回前端**
用户登录成功后，后端不仅校验权限，还需将权限列表返回前端，供 Vue3 全局路由守卫与页面元素权限控制使用，并存储于 `localStorage`（如 `permissions: ["ROOT"]`）。该权限数据仅供前端展示控制，无需提交至后端。`@SaCheckPermission` 的校验完全依赖后端权限数据，不依赖前端传入的权限信息。因此，前端仅需提交 token，无需提交 permissions。

**11. 自定义鉴权类实现**
我们通过实现 Sa-Token 提供的 `StpInterface` 接口，自定义鉴权逻辑，重点实现 `getPermissionList` 方法，以适配项目权限体系。

**12. 双系统独立认证体系**
由于系统包含业务端与 MIS 端，二者必须使用独立的 Sa-Token 认证体系，避免业务端用户登录后误用 MIS 端功能，造成权限越界风险。

**13. Token 传递方式与安全性**
项目未采用 Cookie 传递 token，而是通过请求头传输，主要出于多端适配考虑（PC、移动端、小程序），Cookie 方式通用性不足。在安全方面，我们已防范 XSS 攻击，并全程使用 HTTPS 加密传输，保障通信安全。

**14. 缓存策略**
项目引入 Spring Cache，将热门体检套餐数据缓存至 Redis，提升系统响应速度与用户体验。

**15. 统一响应封装**
统一封装 R 对象作为接口返回格式，规范前后端数据交互。

**16. 全局异常处理器**
自定义全局异常处理器，实现以下功能：
- 异常发生时记录完整日志；
- 向前端返回结构清晰、友好的 JSON 错误信息。

**17. 异步任务生成体检报告**
为提升用户体验，体检报告生成采用异步方式：
- 自定义线程池；
- 在任务方法上添加 `@Async("线程池名称")`，由线程池执行；
- 主入口类添加 `@EnableAsync` 启用异步支持。

关于为何不直接使用 Tomcat 线程池：
- Tomcat 线程池专用于处理 HTTP 请求（接收、解析、响应），无法通过代码提交业务任务；
- 独立线程池可隔离业务处理与请求处理，避免相互影响。

补充问题：线程池拒绝策略是面试常见考点，项目中根据业务场景配置了合适的拒绝策略。

**18. HTTPS 数字证书**
本地开发环境中，我们生成了自签名的 HTTPS 数字证书，用于模拟安全通信环境。

**19. 接口文档规范**
项目集成 Swagger，统一管理并可视化展示 API 接口文档，提升前后端协作效率。

**20. 商品快照的作用**
用户下单时生成商品快照并存入 MongoDB，目的是防止商家后续修改套餐信息导致用户订单详情不一致。用户查看历史订单时，从 MongoDB 读取快照数据，确保信息准确可靠。

**21. 快照复用机制**
商家保存套餐时，根据商品关键信息生成唯一哈希值并存入 `md5_hash` 字段。用户下单生成快照前，系统会先在 MongoDB 中依据该哈希值检索是否存在相同快照，若存在则直接复用，避免冗余存储。

**22. 体检项目导入**
套餐表中的 `exam_items` 字段记录具体体检项目，数据通过 Excel 文件导入，使用 Apache POI 组件完成解析，供体检医生使用。

**23. 文件存储服务**
套餐封面图片、体检项目 Excel 文件及体检报告等均存储在 MinIO 对象存储服务器中。

**24. 套餐删除与异步清理**
删除套餐支持批量操作，需保证所有数据删除的事务一致性（全部成功或全部失败）。事务提交后，再异步执行 MinIO 中封面图片的删除任务，以提升用户体验。若图片删除失败，系统记录错误日志并将失败路径存入数据库，同时通过定时任务定期扫描并重试删除无用图片。

**25. 缓存热点数据**
项目利用 Spring Cache 将热门套餐信息缓存至 Redis。判定标准为“被浏览即热门”。由于体检套餐总量仅数百个，缓存占用内存有限，不会造成资源压力。

**26. 手机验证码发送与防刷机制**
在 Redis 中存储两个键：
- `sms_code_手机号`：有效期 5 分钟，存储验证码内容；
- `sms_code_refresh_手机号`：有效期 1 分钟，用于限制用户重复发送验证码的频率。

**27. 更换手机号流程**
用户需先通过原手机号接收验证码以确认身份，再向新手机号发送验证码以验证有效性，全部通过后方可完成手机号更新。

**28. 套餐列表无限滚动与多条件分页查询**
业务端套餐列表支持无限滚动加载，并支持多条件综合分页查询：
- 套餐名称、编号模糊查询；
- 套餐类型、适用性别精确筛选；
- 价格区间过滤；
- 排序方式：最新、销量、价格升序、价格降序。

**29. 微信支付配置与签名机制**
支付配置项包括：
- `mch-id`：商户号；
- `app-id`：应用标识（小程序、公众号、PC 等）；
- `merchant-serial-no`：商户证书序列号；
- `private-key-path`：私钥文件路径（不可泄露）；
- `app-v3-secret`：APIv3 密钥，用于解密回调数据；
- `notify-url`：支付结果回调地址。

签名流程：
- 我方系统使用私钥对请求进行签名（非加密），表明请求来源合法；
- 微信服务器通过提交的商户证书序列号查找对应公钥，验签确认请求合法性，决定是否放行。

**30. 个人职责说明**
本人独立负责并主导了微信支付全流程的对接与实现，涵盖配置、下单、回调、查询、退款等环节。

**31. 促销规则管理**
体检套餐的促销规则不硬编码在程序中，而是存储在数据库表中，便于动态调整。修改规则后无需重新编译、部署或重启，底层使用阿里巴巴 QLExpress 规则引擎实现灵活计算。

**32. 下单风控措施**
为防止异常交易行为，系统对用户当日行为进行限制：若当天产生 10 笔及以上未支付订单，或 5 笔及以上退款订单，则禁止继续下单。

**33. 支付二维码缓存**
用户点击“继续支付”时，系统优先从 Redis 中获取缓存的 `code_url`。若存在，则直接生成二维码，避免重复调用微信接口，提升响应效率；若不存在，说明支付链接已过期，需重新获取。该机制显著提升了支付流程的流畅度。

**34. 超时未支付订单关闭**
定时任务每小时执行一次，自动关闭超时未支付的订单，作为兜底机制。

**35. Redis 键删除监听**
通过 Redis 键事件监听器，当检测到 `codeUrl` 开头的键被删除时，自动触发对应订单的关单操作。

**36. 支付回调与异步处理**
微信平台通过回调接口通知支付结果。收到通知后，系统立即返回应答，同时通过异步任务更新订单状态，防止回调超时。

**37. 内网穿透调试**
本地开发阶段，使用量子互联等内网穿透工具，使微信平台能够访问本地回调接口。

**38. WebSocket 推送支付结果**
用户扫码支付成功后，系统通过 WebSocket 向前端实时推送支付结果。WebSocket 并非替代 HTTP，而是作为其补充，适用于高频实时交互场景（如支付状态推送），而静态页面仍使用 HTTP 以减少资源消耗。

**39. 支付成功但未收到回调的处理**
若用户付款成功但未及时收到回调（如网络抖动），页面提供“支付成功”按钮，用户点击后系统主动查询微信支付结果，并将真实状态反馈给用户。

**40. 超时关单后实际已付款的处理**
若因网络问题导致回调未及时到达，订单被系统自动关闭，但用户实际已付款，此时用户可联系客服。MIS 端客服可手动同步支付结果，确认付款后将订单状态修正为已付款。

**41. 微信退款功能**
用户发起退款后，系统调用微信退款接口，按原支付路径退回。退款完成后，微信平台通过回调接口通知退款结果，系统据此更新订单状态为已退款。

**42. 退款回调未收到时的补偿机制**
针对退款回调可能因网络延迟未送达的情况，系统通过定时任务定期查询处于“退款中”状态的订单，主动调用微信退款查询接口核对真实状态。若确认已退款，则本地更新订单状态。所有退款处理逻辑均设计为幂等，确保最终一致性。

**43. 退款失败处理方案**
退款可能因用户微信异常、银行卡冻结等原因失败。此时系统无法完成线上退款，用户可联系客服，通过线下转账方式处理，并由 MIS 端手动将订单状态更新为已退款。

**44. IM 即时通讯集成**
为提升客户服务体验，项目集成腾讯云 IM 服务，实现用户与在线客服的即时沟通，避免自行开发的高成本。

**45. 预约限流与缓存设计**
体检机构每日接待量有限，预约规则为次日起 60 天内可约。系统在启动时异步生成 60 天的限流缓存并存入 Redis，目的有二：
- 避免每次预约都查询数据库，减轻数据库压力；
- 无需在数据库中存储默认或无特殊限制的日期数据，节省存储空间。

**46. 限流缓存更新机制**
系统通过定时任务（每日 23:55 执行）动态生成第 61 天的限流缓存，确保 Redis 中始终保有未来 60 天的完整数据。

**47. 防止超卖：Redis Lua 脚本**
预约环节采用 Redis Lua 脚本，将库存读取与扣减操作封装为原子操作，有效防止超量预约问题。我们曾系统梳理并对比了四种防超卖方案，最终选用该方案。

**48. 体检签到与人脸识别**
签到环节需核实体检人本人到场，流程如下：
- 使用鱼住科技读卡器读取身份证信息，SDK 通过 WebSocket 推送给客户端；
- 校验身份证有效期及当日预约记录；
- 开启摄像头现场拍照，并提交身份证照片与现场照片；
- 调用腾讯云人脸识别接口比对是否为同一人，并执行活体检测，防止照片翻拍；
- 核验通过后，将身份证照片录入腾讯云人员库，现场照片上传至 MinIO 作为签到凭证；
- 后续到店可通过摄像头自动人脸识别，推送体检人信息，便于工作人员提供个性化服务。

**49. 体检导引单生成**
前端通过 jsPDF 与 HTML2Canvas 库生成 PDF 格式的体检导引单，工作人员打印后发放给体检人，引导其按序前往各科室检查。

**50. 导引单二维码扫码**
导引单上印有体检编号二维码，工作人员可通过扫码枪快速录入体检人信息，提升录入效率与准确性。

**51. 体检结果存储**
每位体检人的检查结果以文档结构存储于 MongoDB，与体检数据的自然结构高度契合，便于灵活查询与扩展。

**52. 人员调流模块**
系统提供两种调流方式，均衡各科室排队压力：
- **自动调流**：基于权重与实时排队人数计算推荐分值，公式为 `科室分值 = (本科室权重 / 所有科室权重总和) × (最大承载人数 - 实际排队人数)`，分值越高越被推荐；
- **手动调流**：依据科室优先级，优先级高者优先推荐；同级则优先选择权重较小的科室（因其体检效率更高）。

**53. 科室排队人数统计**
各科室门口部署蓝牙信标，当体检人携带手机 APP 接近时，APP 接收信标 ID 并上报后端，系统据此更新 Redis 缓存（key 为 `customer#科室ID`）。定时任务在每日 7:00-16:00 间每分钟执行一次，统计各科室排队人数，并依据调流模式实时刷新科室推荐列表缓存，确保推荐结果实时准确。

**54. 科室推荐列表初始化与刷新**
服务器启动时自动初始化科室推荐列表并缓存至 Redis，后续由定时任务每分钟刷新一次，保证推荐数据始终为最新。

**55. 体检报告生成与存储**
体检完成后第 10 天，系统通过定时任务生成体检报告，并上传至 MinIO 服务器，用户可在业务端查询并下载。

**56. 快递信息自动录入**
快递人员反馈存根后，MIS 端通过 OCR 技术自动识别快递信息并填入系统，减少人工录入成本，提升效率。

**57. Word 格式报告生成**
项目使用 Apache POI 库生成 Word 格式的体检报告，便于打印与归档。

**58. 报告生成调度策略**
由于体检报告生成耗时较长，系统在每日凌晨 1:00 至 5:00 之间，采用定时任务与异步线程分批执行，每批生成 50 份报告，有效分散系统负载。
