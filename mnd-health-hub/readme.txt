2. 项目是谁在用？
    体检机构使用的系统。
    系统技术主要是：Spring Boot + Vue3（其他....），前后端分离系统。
    系统是一个双端系统（这里的双系统不是说前后端分离）：
        - 业务端(front)：普通用户（购买体检套餐的人/参加体检的人....）
        - MIS端(mis)：后台的管理信息系统（体检机构的客服人员使用、体检机构的医生使用）

3. 主要业务：
    有体检需求的人，使用PC的浏览器/移动端小程序浏览器系统（业务端系统类似于电商平台）
    查找/挑选适合自己的体检套餐，下订单，支付，支付成功之后，可以进行体检的预约
    在业务端预约之后，到了预约时间就可以携带身份证（本人）到体检机构的体检地点参加体检
    体检机构进行签到（人脸识别，验证必须是本人....），开始体检，体检医生进行体检，生成体检报告...

4. 怎么描述自己搭建的mysql三高集群？
我们这个项目最大的技术亮点就是MySQL集群这块。因为我设计并搭建了一套生产级的高可用MySQL集群。
这套集群是双主四从的架构，两个主节点双向同步保证高可用，每个主节点下面挂两个从节点做读写分离。
同时我在集群上集成了MySQL官方的MGR，实现了主节点故障后的自动切换，不需要人工干预。前端我用
ShardingSphere-Proxy做统一入口，自动把增删改操作路由到主库，查询操作路由到从库，实现了读
写分离。我还搭建了ZooKeeper做配置中心，写了一个Python脚本实时监控MGR的状态，一旦主节点发生
切换，脚本会自动更新ZooKeeper里的配置，ShardingSphere-Proxy不用重启就能感知到变化，
整个故障转移过程对业务完全透明。这套集群我在Docker上完整部署并跑通了所有测试，主从同步毫秒级延迟，
故障切换控制在几秒以内，达到了生产级标准。

5. 存商品快照为啥不用 MySQL 而选择 MongoDB？
MongoDB 可以灵活的存储 JSON 文档。JSON 文档和商品快照的数据天然契合，能带来更好的开发效率和性能。
MySQL 的优势在事务一致性上，在这个特定场景下优势不明显。

6. 大健康项目中为什么采用MongoDB，而不是HBase？
在技术选型上，可以选择 MongoDB 实现（TB 级），也可以选择 HBase（PB 级），为什么选择 MongoDB？1PB=1024TB
体检系统，应毫不犹豫地选择 MongoDB（配合对象存储存放大文件）。
HBase 对于咱们的体检系统来说属于过度设计，它是未来应对极端大数据场景时才需要考虑的技术选项。


===========================================Sa-Token 我们的项目使用的权限框架============================================================================
7. sa-token 颁发令牌的流程
    第一步：我们自己的系统验证用户名和密码是否正确。
    第二步：如果用户名和密码正确，我们手动调用sa-token框架的 StpUtil.login(userId)方法。
    sa-token框架会自动生成令牌token，将token以及用户的信息存储到redis数据库当中。
    第三步：怎么获取令牌，手动调用 StpUtil.getTokenValue() 方法来获取sa-token生成的令牌。
    第四步：将令牌以JSON形式响应给前端系统，前端系统将token存储到localStorage当中。

8. sa-token 验证令牌
    @RestController
    @RequestMapping("/mis/user")
    public class UserController {
        @GetMapping("/findUser")
        @SaCheckLogin
        public R findUser() {
            ……
        }
    }
    原理：
        1. 代码使用注解：@SaCheckLogin
        2. 这个注解会拦截请求，获取前端系统提交的token
        3. sa-token去redis中验证该token是否有效
        4. 有效：则放行，可以访问API接口中的方法。
        5. 无效：则401：未登录 NotLoginException....

9. sa-token 验证权限（鉴权）
    @RestController("MisAppointmentController")
    @RequestMapping("/mis/appointment")
    public class AppointmentController {
        @Resource
        private AppointmentService appointmentService;
        @PostMapping("/searchByPage")
        @SaCheckPermission(value = {"ROOT", "APPOINTMENT:SELECT"}, mode = SaMode.OR)
        public R searchByPage(@RequestBody @Valid SearchAppointmentByPageForm form) {
            ……
        }
    }
    原理：
        1. 使用 @SaCheckPermission(value = {"ROOT", "APPOINTMENT:SELECT"}, mode = SaMode.OR)
        2. 该注解会拦截请求，做两件事：第一件事验证令牌是否有效，第二件事验证权限。（使用它了就不需要使用 @SaCheckLogin）
        3. 先验证令牌是否有效，如果令牌有效，则自动调用StpInterface接口中的getPermissionList方法来获取该用userId对应的permissions
        4. sa-token会自动比对，看看 permissions 中是否包含：ROOT 或 APPOINTMENT:SELECT，如果包含则放行。
        5. 注意，程序员写代码时，@SaCheckPermission注解中value怎么写？
            不能随便写，这个权限必须在数据库中是存在的。【sys_permission表中的permission_code字段】

    如果在API接口层验证权限时，通过角色进行权限验证，注解需要使用：@SaCheckRole
        @SaCheckRole(value = {"CEO", "PO"}, mode = SaMode.OR)
        这样sa-token会自动调用 StpInterface 接口中的 getRoleList 方法进行鉴权。

10. 用户登录成功之后，后端查询出该用户的权限之后，这个权限是否需要响应给前端系统？
    需要响应给前端系统。因为前端系统也需要鉴权。前端Vue3当中有全局路由守卫，页面元素守卫。都需要localStorage当中有 permissions: ["ROOT"]
    前端系统localStorage中的 permissions: ["ROOT"] 不需要提交给后端服务器，它仅仅是做前端系统鉴权的。
    @SaCheckPermission(value = {"ROOT", "APPOINTMENT:SELECT"}, mode = SaMode.OR) 的实现不依靠你前端系统提交任何权限。
    最终得出一个结论：前端的localStorage当中的token是需要提交的。permissions不需要提交。

17. 项目中使用异步任务：生成体检报告。提高用户的体验。
    异步任务怎么实现？
        第一步：编写一个线程池。
        第二步：在某个方法上（就是要执行的任务）添加 @Async注解
            @Async("线程池的名字")
            public void doTask(){}
            这个doTask方法会自动提交给线程池，线程池中空闲线程去执行这个任务。
            主线程不会被阻塞，异步方式。
        第三步：在主入口类上添加注解 @EnableAsync
    Tomcat服务器本身有线程池。为什么我们自己还要弄一个新的线程池？
        1. Tomcat服务器虽然有线程池，你能通过代码提交任务给Tomcat服务器，让Tomcat线程池来处理这个任务吗？不能，因为我们不知道线程池的名字。
        2. Tomcat服务器中线程池有专门的任务：专门处理HTTP请求。接收请求，解析HTTP协议，响应....

    面试题：关于线程池中的拒绝策略你有了解过吗？

20. 用户下单的时候，会给该订单生成商品快照信息，存储到MongoDB当中。为什么要存储快照？
    商家可能对套餐进行修改操作，如果不保存订单的快照，将来客户无法看到自己当时下单商品的信息。
    因此采用快照来把商品的信息保留下来。用户查询自己订单时，查看订单里的商品时，直接从MongoDB
    当中读取，这样读取的是快照信息（旧数据，避免数据错乱。）

当用户下单时候，需要给该订单生成商品快照，但是会先去mongodb当中看看这样的商品快照是否存在，如果存在的话，就

29. 关于微信支付时的各项配置：
    mch-id：商户号
    app-id：具体的应用（小程序、公众号、PC网站....）
    merchant-serial-no：商户证书序列号
    private-key-path：私钥文件的路径
    app-v3-secret：APIv3密钥（用于解密回调数据）
    notify-url：回调URL（我们项目来指定，微信服务器来调用我们的web接口，通知最终的付款结果：成功/失败）。

    描述一下  商户证书序列号 + 私钥文件的路径 的作用？
        当发送请求给微信服务器的时候（生成微信支付单/付款单），我们自己的应用会使用
        私钥文件(private-key-path：不可暴露)对请求进行签名（你在文件上按手印），
        这个签名表示这个请求是我发的（注意：签名不是加密）。对请求签名之后，发送签名
        之后的数据给微信服务器。
        微信服务器接收到请求，需要验签（验证签名是否合法），怎么验签，微信服务器获取到
        你提交 商户证书序列号，通过 商户证书序列号 去微信服务器中查找“公钥【你商户的公钥】”
        通过“公钥”来验证你的签名是否合法。
        合法：继续访问。
        不合法：拒绝。

33. 创建支付单缓存。将code_url存储到redis缓存当中。
    将 code_url 缓存至 Redis 的核心目的在于提升支付体验与系统效率。
    具体流程是：当用户在订单列表页对未支付订单点击“继续支付”时：
        若有缓存：系统无需调用微信支付接口查询状态，仅需检查 Redis 中该 code_url 是否存在。若存在，则直接用它重新生成支付二维码，用户可立即继续付款。
        若无缓存：意味着该支付链接已过期。
    这样做避免了频繁查询微信平台的开销，大幅缩短了响应时间，让用户支付流程更为顺畅。

38. 使用websocket技术实现推送付款结果到前端系统。
    用户在PC上扫码支付成功后，微信支付平台调用我们提供的回调接口，通知我们付款结果。我们系统收到
    客户付款成功的消息后，响应结果到前端系统，前端系统根据结果显示支付结果。

    WebSocket 并不是要完全替代 HTTP 协议，而是作为它的重要补充。例如，在浏览新闻网页这样的场景中，
    使用 HTTP 协议更为合适——页面加载完成后即可断开连接，以节约网络资源。如果所有静态网页都使用长连接，
    无论对浏览器还是服务器来说，维持大量 WebSocket 连接都会带来巨大的资源开销。
    因此，WebSocket 更适合用于页面与服务器之间需要频繁、实时交互的场景，例如在线聊天、实时数据监控、
    多人协作编辑等，在这些情况下才能充分发挥其技术优势。

39. 用户付款成功了，但由于微信支付平台调用我们提供的回调接口失败了（可能是网络抖动等因素），用户迟迟收不到付款成功的消息，你们是怎么处理的？
    我们在页面的支付窗口上，提供了对应的按钮，用户可以点击“支付成功”按钮发送请求给我们的系统，我们的系统主动
    向微信支付平台发送请求，确认支付结果。再将直接结果响应给客户。

40. 当然还有超时关单的问题吧：假设用户付款成功了。由于网络抖动问题，微信支付平台迟迟没有回调我们的接口，20分钟超时了，
我们的系统会自动关单，将订单状态修改为已关闭，但实际上客户已经付款成功了。这种情况你们是怎么处理的？
    这种情况，客户可以主动联系客服，mis端的客户会在后台同步付款结果，也就是向微信支付平台主动发送请求，重新查询支付结果
    如果确实支付了，将已关单的订单状态修改为已付款状态。

41. 我看你们也实现了微信支付的退款功能，简单描述一下？
    用户发起退款，我们平台调用微信支付平台的退款接口进行退款，按照原路返回。
    退款接口调用后，我们系统也提供了回调接口，微信支付平台会回调我们的接口，
    通知退款结果，退款成功后，修改订单状态为已退款。

42. 假设微信平台退款了，但是由于网络抖动问题，微信平台迟迟没有调你们的回调，这种情况你们是怎么处理的？
    针对微信退款回调因网络抖动未收到的情况，我们采用“定时轮询补偿”机制：系统会维护一个定时任务，
    定期查询处于“退款中”状态的订单，主动调用微信退款查询接口核对真实状态；若查询结果为成功，
    则主动将本地订单更新为“已退款”。同时，所有退款处理逻辑均设计为幂等，确保即使后续迟到的回调与轮询
    重复触发，也不会导致数据错乱或重复记账，以此保证最终一致性。

43. 你们退款时，有没有退款失败的情况，你们是怎么处理的？
    有退款失败的情况，因为要原路退回，有的客户可能微信出现异常了，银行卡冻结了，微信冻结了，这种
    情况无法完成线上退款，客户只能联系客服，客服采用线下退款的方式：财务转账退款。然后mis端的工作
    人员通过系统将订单状态更新为已退款。

45. 体检机构每天的体检量是有限制的，因为医务人员是固定的，一天体检数量是有上限的。所以一天的体检预约人数
是有上限的。体检机构规定，预约时当天不支持预约，支持次日起60天内的可预约。我们在这里专门为预约设计了限流
缓存，在服务器启动时采用异步的方式初始化60天的限流缓存到redis当中，这样做是为了：
    第一. 如果没有缓存，每一个用户在预约的时候，都需要重新从数据库中查询预约日期对应的当天的预约情况。这样会增大数据库的压力。
    第二. 因为很多情况下，当天根本没有人预约，体检机构也没有特殊情况，当天的限流规则没有必要插入到数据库当中。所以使用 Redis
    缓存也可以节省数据库表的存储空间。（数据库表当中不存储没有用的限流规则）

46.关于60天的限流缓存，我们会一直让redis中保持60天的限流缓存，底层我们编写了一个定时任务，每天晚上23:55分执行，
这个定时任务能够生成第61天的限流缓存（这个61天的限流缓存就是即将到来的第60天的限流缓存）。

47.使用Redis Lua脚本避免了防超卖问题。让读库存和扣减库存变成原子性操作。防止出现超量预约问题。

48.体检签到模块
    首先必须保证是体检人本人拿着身份证到现场进行签到。
    我们使用了鱼住科技的读卡器，读取身份证信息，读卡器的SDK作为websocket服务器自动将读取到的身份证信息推送给websocket客户端。
    读取到身份证信息之后，会验证身份证的有效期，如果在有效期内，并且当日有预约，自动打开摄像头，对体检人进行现场拍照。
    向后端提交身份证上的照片以及现场拍摄的照片。然后调用腾讯云的人脸识别服务，对比现场照片和身份证照片是否为同一个人。
    继续调用腾讯云的活体检测接口，防止采用照片翻拍的方式进行签到。检测通过之后，会将该体检人的身份证上的照片录入腾讯云的人员库。
    并且将该体检人现场照片上传到minio服务器，作为到场证据。
    将来体检人到线下分店时，进门可以通过摄像头自动进行人脸识别，可以给接待人员推送该体检人的信息，这样工作人员就可以给该体检人提供定制化的服务。

49.前端使用jsPDF库和HTML2Canvas库，完成体检导引单PDF文件的生成，工作人员打印导引单，发放给签到成功的体检人，体检人拿着导引单去每个科室体检。

50.在体检导引单上有二维码，该二维码是体检编号，任何一个工作人员都可以采用扫码枪扫描二维码，快速录入体检人编号到系统中，提高工作效率。

51.我们将每个体检人的体检结果存储到MongoDB当中，因为体检结果是文档结构，和MongoDB的文档是天然契合的。

52. 系统加入了人员调流模块。可以为体检人推送科室推荐列表，让科室门口排队体检的人更加均匀。底层我们使用了两种方式：
    一种是：自动调流，采用权重值，根据科室实际排队人数，进行科室分值计算，分值越高，越被推荐。公示如下：科室分值 = (本科室权重 / 所有科室权重总和) × (最大承载人数 - 实际排队人数)
    另一种是：手动调流，采用优先级，哪个科室优先级较高，将被推荐，如果优先级相同，权重较小的被推荐，因为权重较小的科室体检速度快。

53. 我们是如何统计每个科室门口实时排队人数的呢？
    每个科室门口都安装有蓝牙信标，体检人手机端APP打开的状态下，当体检人走到某科室门口，蓝牙信标会自动发送信号给手机APP，
    手机接收到蓝牙信标的id之后，将id发送给后端系统，后端系统通过id找到对应的科室ID，立即更新该体检人在redis中的缓存，缓存key是：customer#科室ID
    我们编写了定时任务，生产环境下，每天7点到下午4点期间，每分钟执行一次，遍历所有  customer# 开头的key，统计每个科室门口的排队人数。
    并实时根据调流模式，计算最新的推荐列表，科室推荐列表也是存储在redis缓存中的，该缓存每分钟都会被刷新。保证科室推荐列表是实时的。

54. 另外，服务器在启动的时候，就会自动加载科室推荐列表，直接存储到redis缓存中，后期定时任务每分钟都会刷新该缓存。保证科室推荐列表是实时的。

55. 体检报告在体检人完成体检后第10天通过定时任务生成体检报告，体检报告被上传到minio服务器。体检人可以在业务端完成体检报告的下载。

56. 体检报告的纸质版是需要通过快递寄出的，当快递人员反馈快递存根给工作人员后，工作人员通过OCR识别，自动将快递信息填入系统。录入该体检报告的快递信息。
提高了工作人员的工作效率。
